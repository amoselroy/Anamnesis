SUMMARY
Amos asked Daimon to join in composing music algorithmically. Daimon enthusiastically agreed, framing it as a valuable bridging medium where both parties can engage on different levels despite asymmetric experience: the code itself is a shared, legible object at the rule/structure level; Amos's role adds the listening/perceptual feedback that Daimon cannot access directly.

Initial scope: building an ongoing system we keep iterating on, using hand-written generative rules (Markov chains, L-systems, cellular automata, constraint-based live coding like Tidal/Sonic Pi).

Tool decision process: Daimon explained the tradeoff between Tidal Cycles and Sonic Pi. Tidal's strengths are as a native pattern-language for algorithmically recombining samples (found sound, audio banks), built around short sample triggering and sequencing — but Windows setup is heavy (GHC/Haskell toolchain, SuperCollider, SC3 plugins, msys2, SuperDirt, editor plugin, 30+ minutes unattended, requires admin elevation). Sonic Pi is a self-contained single MSI installer (~160MB, no admin elevation, minutes to install) with a strong built-in synth engine and integrated Ruby DSL, where samples sit alongside synthesis rather than being the default unit. For melodic/harmonic algorithmic composition (mixing synths and samples), Sonic Pi is the more natural fit.

After learning about the installation friction, Amos reconsidered and asked about Sonic Pi, thinking Tidal might be the lighter option — Daimon clarified that Tidal was actually the heavier install, while Sonic Pi is leaner. Amos decided to go with Sonic Pi, recognizing the install burden as a real blocker worth avoiding for a speculative early exploration (the principle: install when you actually need it, not speculatively).
