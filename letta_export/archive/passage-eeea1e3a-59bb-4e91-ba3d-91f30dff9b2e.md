SUMMARY
Amos spent extended time studying the agency migration plan schema and asked clarifying questions about the fundamental structure. He confused "PK" initially, but quickly recalled it means Primary Key and understood why each table needs an `id` field separate from its functional keys. He grasped the purpose of `UINN` as a matching key (how to find which therapy a record belongs to) versus `id` as a reference key (how other tables point to specific rows). He noticed that `therapy_aliases` now has a type column to separate `inn` (for regulatory/trial matching) from `display` (for UI search), and asked what NULL meant — the answer is legacy data before the column existed, treated as `inn`. He then asked a sharp question: **isn't `therapy_status` redundant with the new `therapy_approvals` and `therapy_trials` tables?** The honest answer is yes, partially — the agency data columns are doing a job that belongs in the new tables. This led to a simplification: instead of keeping `therapy_status` as a "curator table" with only `lifecycle` and `last_synced_at`, those two columns can simply move to the `therapies` table in Phase 0, allowing `therapy_status` to be dropped entirely in Phase 3. This is cleaner and simpler than the original conservative plan. The migration plan was updated to reflect this. Amos then asked a deeper architectural question: could the pipeline eliminate both `agency_approvals` and `trial_records` tables by writing directly to `therapy_approvals` and `therapy_trials`? Daimon explained the constraints: FDA publishes hundreds of thousands of approval records — the pipeline downloads bulk data, stores it temporarily, then runs matching to figure out which records belong to which therapy. Without a persistent import table, unmatched records are discarded and can't be re-matched when new therapies are added. Additionally, the `UNIQUE(agency, record_key)` constraint on `agency_approvals` prevents duplicate imports — moving that constraint to `therapy_approvals` wouldn't work because you can't guarantee uniqueness without therapy_id matching context. The trade-off: the bulk CSV approach requires intermediate tables and stores hundreds of thousands of records; a per-therapy API query approach would eliminate intermediate tables but require N API calls per sync. Amos noted that bulk storage of hundreds of thousands of records might push Braindexer out of the free Neon tier and asked whether condition filtering could at least reduce volume. This question was flagged as worth running by Opus for a hybrid solution — per-therapy queries for active conditions only, combined with periodic bulk syncs for reference. The session ended with this question open: Amos wants to explore alternatives rather than commit to the hundred-thousand-record bulk storage approach, and Daimon offered to consult with a larger LLM for hybrid architecture ideas.
