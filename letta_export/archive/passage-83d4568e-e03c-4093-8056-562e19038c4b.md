SUMMARY
A critical architectural recognition emerged: status information was scattered across three tables (`therapies.status`, `therapies.evidence_level`, and `therapy_regulatory_status`), creating inconsistency and maintenance burden. The user identified that the monitoring-generated regulatory data (`therapy_regulatory_status` — fda_status, ema_status, ct_phase, etc.) should be unified with lifecycle state (active/draft/discontinued/withdrawn) and evidence level into a single source of truth. Stage 1 implementation involved: (1) renaming `therapy_regulatory_status` to `therapy_status` in `setup_db.py`, (2) adding `lifecycle` and `evidence_level` columns to consolidate previously scattered fields, (3) backfilling `lifecycle` from `therapies.status` and `evidence_level` from `therapy_conditions`, (4) updating `agency_monitor.py` to write the consolidated table, (5) updating `admin.py` confirm/approve/reject operations to write to `therapy_status` alongside `therapies` for backward compatibility. The result: one table per therapy containing the complete regulatory and lifecycle picture. `therapies` table retains mirror columns (`status`, `evidence_level`) for now to avoid breaking existing router queries — these become purely derivative in Stage 2. The migration revealed a subtle ordering issue in `setup_db.py` (the CREATE TABLE IF NOT EXISTS ran before the DO block containing the rename), solved by manual data migration after both objects existed.
