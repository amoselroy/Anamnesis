WORLD PATTERN 2026-06-25 — Data existing in storage but invisible in API until explicit wiring is added — 2026-06-25

PRINCIPLE: The presence of data in a database does not create API visibility; exposure requires explicit query and response modeling, and absence of that wiring produces silent nulls rather than errors.

NARRATIVE: The therapy_status table was being populated correctly by sync_therapy_from_existing_imports, but the therapies router had never been updated to JOIN that table and include agency_status in the response. The API response contained an `agency_status` key with null values. The nulls were silent — the API succeeded, the response was valid JSON, everything looked fine. Only by checking the actual API response against the database did the gap become visible. This pattern differs from schema mismatches (which cause 500 errors): here the data existed, the table was correct, but the API surface hadn't been wired to expose it. It's a reminder that completeness of data and completeness of data access are separate concerns. Applies to any system where multiple layers must coordinate on exposure: REST APIs, GraphQL schemas, data warehouse views, anything with a consumer layer reading from storage.
