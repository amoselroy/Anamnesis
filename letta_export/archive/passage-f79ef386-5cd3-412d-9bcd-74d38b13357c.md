SUMMARY
NARRATIVE SUMMARY:

Amos identifies a duplication in the system: the hook was reconstructing a conversation transcript from structured data and saving it to the pending file, but Claude Code already saves a complete JSONL transcript of every session. Why maintain two separate transcript sources?

**The Insight**: Claude's native JSONL is the source of truth for what happened in a session. It's complete, permanent, and available between sessions. The pending file doesn't need to duplicate that data — instead, it can store just the path and byte offsets to the Claude transcript, plus metadata about which offsets have been archived.

**Design Pivot**: Replace `conv_text` (the reconstructed transcript) in pending files with `claude_transcript_path` (path to the JSONL) and `start_offset`/`end_offset` (byte positions). The worker reads the Claude JSONL file directly, extracts the byte range, and passes that text to Letta for segmentation. For pre-compacted sessions, `end_offset` points to the compaction point; for session-end blocks, it points to EOF.

**Handling Migration**: Old pending files that still contain `conv_text` are handled gracefully — the worker detects them and uses the embedded text as a fallback. New pending files use the offset approach, which is more resilient (survives Claude's automatic transcript management, doesn't duplicate storage).

**Context Impact**: Using offsets instead of embedded text has zero impact on new-session context size. The pending file becomes lightweight metadata rather than a full transcript copy.

**Metadata Integration**: The design allows embedding additional structured metadata into the JSONL itself (via Claude's API if available), eliminating the need for external metadata tracking. This further consolidates the system.
