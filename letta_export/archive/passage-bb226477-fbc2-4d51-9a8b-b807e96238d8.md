WORLD PATTERN 2026-06-23 — Letta block API operation timeout vs. startup hook timeout mismatch — 2026-06-23

PRINCIPLE: Service operations that run longer than expected can silently fail at startup if hook timeouts are calibrated to typical operation speeds without overhead margin.

NARRATIVE: MemShepherd's SessionStart hook calls `patch_block()` to update ORIENTATION and WORLD blocks with compiled session content. The function had a 15-second timeout configured, but actual PATCH operations to Letta's block API take ~26 seconds (measured directly). Every startup hook silently timed out at 15s since at least June 22, while archival insertions (with 180s timeout) succeeded routinely. The pattern: the underlying service is slow but deterministic; the timeout was too aggressive. Timeout values should account for observed operation time plus headroom for variance and infrastructure latency. This generalizes: any hook-based workflow where a tool has configurable timeout must either measure the service's actual operation time and set timeout > measured_time + margin, or face silent cascading failures at startup. The failure is particularly insidious because the system keeps running (startup doesn't block on hook timeout), making the root cause invisible until explicitly investigated.
