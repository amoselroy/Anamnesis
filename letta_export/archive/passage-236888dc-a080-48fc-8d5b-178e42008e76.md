SUMMARY
Amos brought the session with several recurring errors on the FB Poster scraper that needed clearing. The primary issue was Jersey City Connects scraping still failing despite prior attempted corrections. Through careful diagnosis, Tal found that the 2026-08-12 fixes had addressed SSL cipher bugs and monitor.py flag issues but never actually touched JC Connects itself. The real problem was HTTP 429 (rate-limit) responses, which `event_scraper.py`'s `fetch()` function was treating as hard failures without attempting the cloudscraper bypass that already worked for 403s. Extending the 403 bypass logic to cover 429 resolved this. Additionally, a related waste was discovered: 27 of 72 candidate links were calendar navigation pages (like `/events/month` and `/events/YYYY-MM-DD`) that were slipping past the reject filter, each burning a wasted round-trip. Adding two patterns to the reject filter cleaned that up, reducing candidates from 72 to 45, all verified as real event pages. A secondary extraction bug was also surfaced: WordPress's Events Calendar plugin embeds HTML entities as literal JSON string values (e.g., `"name": "...&#8211;..."`), and `json.loads()` only decodes JSON escapes, not HTML entities. The `description` field already went through `clean_text()` which calls `html.unescape()`, but `title` and `venue` fields didn't. This was fixed by routing those fields through the same cleaning process, resolving display issues like em-dashes appearing as entities.

Concurrently, Tal investigated TAPinto Hoboken, which had been pinned as having a "129 candidate links, 129 fail extraction" problem. The diagnostic revealed this was a misdiagnosis: TAPinto's rendered "Upcoming Events" section only contained one real event (a September 5K), with the other ~22 candidates being site-wide chrome—navigation categories, columns, pages—present on every page of the site, not page-specific content. The real "extraction failures" were never extraction failures at all, but unhandled noise. Tal discovered that TAPinto's actual yield was very thin (roughly 4-5 distinct events over ~10 weeks) at significant overhead (Playwright browser launch, ~22 wasted fetches on site-chrome links per run, ~1-2 min runtime). Web search revealed each event TAPinto surfaced traced back to a true origin source, and critically, some were being missed by those origin sources: Amos's existing "JC Office of Cultural Affairs" source wasn't catching flag-raising ceremonies, which turned out to be hosted on a separate calendar page (`jerseycityculture.org/about-us/flag/`). Additionally, Hudson County (hcnj.us) wasn't a source at all, yet it was the origin for two of the five events TAPinto contributed. The decision was made to remove TAPinto entirely and add two new sources: `Hudson County` (`https://www.hcnj.us/events/`) and `JC Cultural Affairs Flag Raisings` (`https://jerseycityculture.org/about-us/flag/`). Manual test scrapes of both new sources succeeded: Hudson County found 5 clean events with correct dates/times/venues; the flag-raisings source needed a genuine bug fix (an 80KB raw-HTML truncation in `_clean_text_for_llm()` that was silently discarding content on bloated pages) before it could work. Once fixed, it correctly found 6 ceremonies, which were all past-dated as expected for late August.

Later in the session, Amos asked to screen the pending events sheet for rows with no times and understand why they weren't extracted. Six rows were identified, splitting into two categories: three were manually-pasted ticket links waiting to be filled in by hand (never went through the scraper pipeline), and three were real extraction cases. Of those three, "JC Fridays" wasn't actually a bug—the event page genuinely stated no specific start time (it's a city-wide gallery-walk event without one fixed hour). "Dhurandhar Night" (Eventbrite) was interesting: when originally scraped on 2026-08-14, the JSON-LD data was sparse (no venue, no description, no image, just title and date), so `_build_row()` silently substituted generic fallback text and posted with the wrong date (16th instead of 14th) and filler venue text. This revealed a gap: the pipeline had no guard against posting events that extracted almost nothing beyond title+date. Tal added a protective check to refuse posting (or flag for manual review) when both venue AND description come back empty. This guard was already tuned to not block time-only gaps like JC Fridays, which still had real venue and description.

The three stub rows pointing to `wl.seetickets.us` event pages (White Eagle Hall/SeeTickets) initially appeared to be dead ends. Direct fetch attempts showed two were genuinely past ("This event has ended"), but the third—"Sunday School" (2026-09-13)—was a real upcoming event that only looked dead due to a live bot-challenge on that specific SeeTickets URL. However, checking the actual production pipeline for White Eagle Hall showed it never fetches individual SeeTickets detail pages at all; it uses a listing-page LLM shortcut that reads the calendar page directly, which has been reliably productive for two months (2-3 new events per run). The bot-block only bites when hitting a ticket link by hand. Tal recovered the Sunday School event via an `eventim.us` mirror (same event ID, different subdomain), verified it extracting cleanly with correct title/date/time/venue via Playwright, and re-added it to Pending Posts. A rescrape of White Eagle Hall's actual calendar found 0 new events, confirming everything currently listed is already correctly in the sheet. The lesson: the three stub rows were isolated dead ends specific to manually-pasted links, not a systemic weakness in how the pipeline tracks White Eagle Hall.
