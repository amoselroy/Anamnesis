SUMMARY
Amos initiated a Braindexer code review using Fable 5, scoped to core app code plus agency migration and roadmap documentation, with instructions to flag current-build risks and future-phase concerns separately. The review returned within ~300 seconds with comprehensive findings across three sections. Daimon verified the two most critical findings against actual codebase before presenting results. Finding #1 (CRITICAL security): `routers/sources.py` and `routers/relationships.py` have no `require_curator` dependency on any endpoint; POST/PUT/DELETE operations on sources and relationships are completely unauthenticated and accessible to anyone on the internet. A public `DELETE /sources/{id}` performs hard deletion, bypassing the soft-delete/curation design pattern used elsewhere. Finding #2 (HIGH, data corruption): `set_condition_scores` allows curator overrides of effectiveness/evidence scores and summaries, but `research_therapy` and `generate_summaries` unconditionally overwrite these same columns on next run, with COALESCE protection applied only to `evidence_level`. This duplicates the null-clobber bug class already fixed in `_upsert_status`, directly undermining planned Phase II/IV audit-status work. Additional HIGH findings include silent migration error-swallowing in `main.py` (no logging of failed migrations, leaving schema drift invisible), unauthenticated public access to `/therapies/search` endpoint triggering paid Voyage API embedding calls on arbitrary input (cost/abuse vector given existing budget constraints), news-to-therapy matching via substring that can misattribute articles with short aliases, and background daemon threads vulnerable to Render free-tier spin-down killing mid-flight jobs without checkpoint. The review also identified architectural conflicts between two planning documents: `ROADMAP.md` describes OAuth + full accounts + clinical-review-first (Phase III/IV path), while `pseudocode.md` describes lightweight email-token auth + newsletter-first (Phase 4/5 path), with different auth mechanisms, phase numbering, and product direction. Root cause connecting multiple future-phase issues is summary/score rewriting without versioning history — Phase IV `claim_annotations` and Phase II `summary_flags` both assume stable summaries, but they're completely overwritten on regeneration, creating orphaned annotations/flags.
