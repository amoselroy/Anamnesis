SUMMARY
The session began with continued implementation of the agency monitor service after setup_db.py migrations were complete. Initial implementation used file-based CSV snapshots stored in `agency_data/snapshots/`, but critical realization emerged: Render's free tier has ephemeral filesystem — all non-git files are wiped on every deploy, making CSV snapshots unsurvable. This forced architectural pivot: snapshots moved from filesystem to Neon database in a new `agency_snapshots` table, storing raw 60K rows from FDA, EMA, ANVISA, and ClinicalTrials.gov. The monitor seeded all four sources successfully, generating 16 therapy regulatory statuses and 7 initial status suggestions (including one false positive for Cu(ATSM) matched against 1984 FDA copper supplement data, demonstrating alias matcher surfaces candidates for curator review). EMA exhibited intermittent 404 errors during seeding, initially appearing transient but actually reflecting a website migration that broke old `/en/documents/report/` paths between January-June 2026.

User recognized the 60K-row snapshot approach was suboptimal and proposed a cleaner three-table architecture: `agency_import` (staging table, full agency download replaced each run), `therapy_regulatory_status` (stable, one row per therapy with consolidated status across all agencies), and diff logic comparing new imports against the stable table before updating it. This eliminated the need to store 60K historical rows and simplified matching and suggestion generation. Implementation with this design generated identical legitimate signals while being more maintainable. The new architecture is Render-safe: both tables live in Neon and persist across deploys.

Attention then shifted to handling Render's free tier's 15-minute automatic sleep window. Any scheduled job that would fire after 15 minutes of inactivity will never execute because the dyno is dormant. The monthly cron job needed all retries to occur synchronously within that window. Solution: three retry attempts with 4-minute spacing initially (4+4+1+4+1 = 14 minutes worst-case), then refined to 3.5-minute spacing (4+3.5+1+3.5+1 = 13 minutes) to add safety margin. Failure handling: admin notification flag set immediately on first failure, cleared automatically if any retry succeeds, remains set if all three attempts fail. Manual trigger endpoint `POST /admin/run-agency-monitor` with `?failed_only=true` parameter allows curator to retry from admin panel without waiting for scheduled window. This approach trades some retry sophistication (no staggered DateTrigger retries across hours) for guaranteed execution within one dyno wake-up cycle.

EMA data source emerged as problematic. The static URL provided earlier (`https://www.ema.europa.eu/en/documents/report/medicines-output-medicines-report_en.xlsx`) worked during initial inspection but later returned 404. Investigation via Wayback Machine confirmed EMA migrated their website between January and June 2026, breaking all old static document paths. Their new site is Drupal-based with JavaScript rendering, making the actual download link inaccessible via plain HTTP requests. The archive has a January 2026 copy (7 months stale), but static HTTP download no longer exists. Three options emerged: (1) use Wayback Machine archive (too stale), (2) use Playwright for browser automation to navigate the JS-rendered download (memory concerns on 512MB Render free tier), (3) skip EMA until URL surfaces (lose European approval/withdrawal data). Playwright was viable but adds ~200-350MB memory footprint; mitigations using `--no-sandbox --disable-dev-shm-usage --single-process --disable-gpu` flags reduce to ~150-200MB, but still risky on 512MB total. User noted this could be solved by running EMA download locally (separate process) and importing the file, or waiting for paid Render upgrade after fundraising. Critical observation at session end: user questioned how EMA was downloaded earlier if URL is broken now, suggesting the static URL may still be functional despite intermittent 404s.
