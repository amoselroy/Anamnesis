WORLD PATTERN 2026-06-29 — Foreign key CASCADE deletion cascading failures in multi-dependent schemas — 2026-06-29

PRINCIPLE: When an entity has dependencies in multiple tables without CASCADE delete configured on all of them, DELETE operations fail with 500 even though the failure appears to be a system error rather than a constraint issue.

NARRATIVE: Amos needed to delete Donepezil from Braindexer's database to demonstrate the therapy creation pipeline live during the Dr. Sano call. The delete UI returned a 500 error. Investigation revealed that `therapy_status` and `status_suggestions` tables referenced therapies without CASCADE delete configured. Fixing required editing the delete function to add CASCADE to both dependency paths (one-line fix), committing, and waiting for deployment. The problem surfaced as a generic 500 in the UI — the foreign key constraint was being violated silently rather than surfacing as a clear constraint error. This pattern recurs in any complex multi-table schema where an entity is referenced in multiple places: the first delete operation succeeds on the primary table, then fails on dependent tables, and the error message doesn't clearly identify which table blocked the operation. Proper fix requires cascading all dependent deletes or explicit cascade statements in the DELETE query.
