WORLD PATTERN 2026-06-10 — Filter mode state persistence causing unexpected behavior in multi-mode UIs — 2026-06-10

PRINCIPLE: When a UI component has multiple filter modes (search vs. browse/list), state tracking the active mode can persist and cause unexpected behavior when switching between modes, especially if the modes have different data requirements.

NARRATIVE: The Braindexer index page has two filter modes: (1) search via embedding similarity, requiring `t.embedding IS NOT NULL`, and (2) list/browse via condition filter, which has no embedding requirement. When a user performed a search first, then tried to use the condition filter, the `currentMode === 'search'` flag persisted. The `onFilterChange()` function checked this flag and called `doSearch()` instead of `loadList()`, applying the search mode's embedding filter to the condition filter operation. Since no therapies had embeddings yet (pre-Research & Summarize), this returned zero results. The user expected the condition filter to show all therapies linked to that condition, but got zero instead. The root cause wasn't in the database or backend, but in frontend state not being reset when switching between modes. This pattern recurs in any multi-modal filtering UI: each mode may have different preconditions or data requirements, and switching modes requires explicitly resetting state or gating behavior on which mode the user intends to be in at that moment, not which mode they were previously in.
