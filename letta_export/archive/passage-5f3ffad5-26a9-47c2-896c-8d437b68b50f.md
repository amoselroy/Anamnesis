WORLD PATTERN 2026-06-11 — Log file write lock on Windows Task Scheduler with batch file redirect — 2026-06-11

PRINCIPLE: When a batch file redirects stdout to a log file, it holds an exclusive write lock that prevents Python from opening the same file simultaneously, causing silent failures on scheduled runs that work fine in manual terminal execution.

NARRATIVE: The Event Scraper worked perfectly when run manually in the terminal but failed on every nightly Task Scheduler run for 3 days with `PermissionError` on the log file. The root cause was that the batch file redirect (`>> event_scraper.log 2>&1`) held an exclusive lock while Python's `log()` function tried to open the same file for writing. Both approaches had existed since the initial commit, but the conflict only surfaced when running through Task Scheduler (where the redirect is active) versus manual terminal runs (where there is no competing lock). The fix was removing file-writing from the Python function and letting `print()` output flow through the batch redirect. This pattern generalizes: any application-level write to a file that the shell is actively redirecting to will fail with mutual exclusivity errors. The lesson is that shell-level stdout redirection and application-level file writes to the same file are mutually exclusive on Windows.
