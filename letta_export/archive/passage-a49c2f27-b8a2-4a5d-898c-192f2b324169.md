WORLD PATTERN 2026-06-19 — NCBI API key registration as cleaner than inter-request delays for PubMed rate-limit management — 2026-06-19

PRINCIPLE: When facing API rate limits on a service that offers free API key upgrades, registering a key (one-time setup) is preferable to implementing inter-request delay loops (ongoing execution cost).

NARRATIVE: Initial PubMed rate-limiting fix added 0.4-second delays between alias queries (12 calls across 6 aliases × 2 PubMed endpoints = rate limit at 3 req/sec free tier). This worked but added ~5 seconds to each research run. Discovery that NCBI offers free API keys bumping the limit to 10 req/sec led to a one-time registration and environment variable setup. The code was already prepared to read and use the key automatically. Result: no delays needed, 12 requests complete in under 2 seconds without hitting rate limits. The pattern generalizes: when facing rate limits, check whether the API provider offers free tier upgrades (keys, higher limits, etc.) before implementing client-side throttling. One-time setup beats ongoing execution cost if available. The cost/benefit inflection point is roughly: if the service will be used repeatedly and the rate limit is a permanent constraint (not temporary overload), upgrade the tier rather than throttle.
