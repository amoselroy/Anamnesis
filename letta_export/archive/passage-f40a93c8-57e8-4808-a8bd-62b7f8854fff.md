SUMMARY
This session represents a sustained, multi-phase development effort spanning approximately 18+ hours to build out a complete automation infrastructure for extracting event and exhibition data from heterogeneous web sources for social media posting.

**Architecture and Technical Foundation**: Amos requested rebuilding an event scraper that was previously running on Tasklet.ai. After reviewing the existing pseudocode, the core challenge was identified: 44 event sources with no standard schema.org JSON-LD structure, each using different HTML patterns, CMS platforms, and JS rendering approaches. Rather than building a single universal parser, I designed a layered fallthrough architecture with progressive complexity:
- Path A: Static HTML/CSS selector parsing (zero cost, ~2 seconds)
- Path B: Claude Haiku LLM extraction on listing pages for hard cases (~$0.01 per page)
- Path C: Playwright for JavaScript-rendered sites (~5-10 seconds)
- Graceful failure for truly inaccessible sources

This hybrid approach balanced cost efficiency (keeping nightly expenses to $0.01–0.03) with reliability across heterogeneous sources. The scraper writes directly to the local xlsx file (`JC and Hoboken Events.xlsx`) following the same pattern as existing posting systems, reading source rotation from "Events Primary Sources" sheet and writing results to "Pending Posts."

**Debugging and Source Validation**: Testing exposed a complex landscape of source failures. White Eagle Hall (SeeTickets widget) had events only on the listing page with external ticket links, requiring Path B LLM extraction. WFMU initially appeared to be pure Eventbrite with JS-rendering but investigation traced its actual organizer ID (20054583239) to the real Eventbrite page. Hoboken Library and JC Library were identified as pure JS-rendered LibCal installations requiring Playwright. Three sources (Hoboken Now, JC Downtown, Hoboken Girl) returned 403 Cloudflare protection errors which playwright-stealth could not bypass—further investigation determined these were aggregators or empty platforms pulling from primary sources already in the list. Hudson Reporter's URL was corrected from a 404 to `/events/` endpoint, and City of Hoboken Recreation was fixed to `/Community/Calendar`. The pattern emerged that JS-only sources fell into two categories: genuinely inaccessible (Cloudflare bot protection, cross-origin embeds) versus technically renderable with Playwright.

**Strategic Pivot to Source Discovery**: Rather than continuing to fight bot-blocking on aggregator sites, the decision was made to use aggregators as discovery tools. Systematic web searching of missing events mentioned on Hoboken Now (Sinatra Park concerts, Church Square Park concerts, Movies Under the Stars, Fitness in Park) led to discovery of seven new primary event sources not previously in the scraper: Church Square Park Concert Series, Hoboken Farmers Market, JC Night Market, Hoboken Family Alliance, Destination Jersey City (identified as the richest source with 50 links and 23K chars), TAPinto Hoboken (JS-rendered but accessible), and Pier 13 Hoboken (primary website DNS failure). This research pivot increased total source count from 38 to 45 and demonstrated a generalizable principle: use blocked aggregators for discovery rather than direct extraction, yielding higher-quality data from official venue sites.

**Facebook Events Handler Implementation**: Pier 13's website unavailability prompted creation of a specialized scraper path for venues with active Facebook events pages. A Facebook events handler was built using the existing `facebook_session_personal.json` session (reused from fb_poster.py and brokerage_sharer.py), loading venue events pages via Playwright and parsing the structured event text format Facebook displays ("Sat, Jun 20 at 12 PM / Event Title / Venue Address"). Testing on Pier 13's Facebook page successfully extracted 4 upcoming events with correct dates, times, and venue information. This handler creates a generalizable pattern: any venue with a thin or inaccessible website but active Facebook events page can be added to the sources sheet as a Facebook URL, immediately becoming scrapable without additional coding. Rate limiting was considered at 1–2 Facebook sources per run to avoid bot detection.

**Parallel Exhibition Scraper Development**: A companion `exhibition_scraper.py` was built to handle the "Exhibitions Pending" sheet with different schema (start/end date ranges instead of specific datetimes, permanent exhibit flags, periodic re-posting). Using similar 5-path architecture but optimized for multi-day/open-ended shows, it focuses on extracting start and end dates using Haiku LLM. Critical discovery: Hoboken Historical Museum's Squarespace site required special handling—Playwright's `load` strategy fired before JS execution completed, but `networkidle` + 30s timeout successfully rendered full page content. A subsequent issue exposed HTML truncation at 80,000 characters cutting off exhibition content; this was increased to accommodate Squarespace's verbose DOM structures. Testing extracted 23 new exhibitions: 12 from Liberty Science Center (permanent exhibits including Thomas & Friends), 2 from Hoboken Historical Museum with proper titles and date ranges, 9 from Mana Contemporary with accurate start/end date extraction. Exhibition scraper was scheduled for weekly execution (versus nightly for events) since exhibitions change slowly.

**Tracking Architecture Refactor**: Late in the session, a design insight emerged: rotation tracking was being managed in a hidden SQLite database (`scrape_tracker.db`), conflicting with the principle of using the local spreadsheet as single source of truth. The refactoring involved removing all SQLite code from both scrapers, adding two new columns to each source sheet (`Last Scraped` for rotation ordering and `Last Count` for monitoring), and reading/writing directly to the spreadsheet instead. This change made scraper activity visible and editable directly in Google Sheets, eliminated an external dependency, and aligned with existing system architecture of treating xlsx as authoritative state.

**Deferred Feature - Source Failure Alerting**: At session end, need was identified for a catch-all mechanism to detect when sources stop working or change in ways that cause scraping failure. Design specification was documented: track `consecutive_zeros` and `last_successful_date` per source, alert via email to aelroy@gmail.com after N consecutive zero-result runs (3 for events ≈3 days, 5 for exhibitions ≈5 weeks), distinguish legitimate "no events" from "site broken" by looking for fetch errors alongside zero results, send alerts via Gmail SMTP with App Password env var. Implementation deferred because it overlaps with tracking refactor work and session was at capacity.

**Key Insights and Principles Captured**: Layered fallthrough architecture with increasing cost/sophistication is more efficient than universal parsers or custom code per source. Local spreadsheet as single source of truth for both configuration and runtime state provides visibility and enables operators to directly edit system state. Cloudflare bot protection is genuinely unbypassable via headless automation—practical approach is graceful degradation (detect 403, skip source, move to next). Using aggregators for source discovery rather than direct scraping is faster and yields higher-quality data. Playwright page wait strategies for JS-heavy CMS require empirical testing; `networkidle` is slow (~10+ seconds) but reliable for complete JS execution. HTML truncation limits must accommodate verbose DOM structures of modern CMS platforms.
