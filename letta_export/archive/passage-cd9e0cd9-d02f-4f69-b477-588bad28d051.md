SUMMARY
Fable's convergence investigation flagged an unaddressed security exposure: the Letta REST API port (8283) was not localhost-bound and had no authentication, leaving it accessible from the LAN with no credentials required. This had been identified in earlier analysis (private/FABLE_FINDING5_PROXY_ANALYSIS.md, 07-07) but not yet implemented.

Amos and Daimon designed a two-part hardening strategy using Letta's built-in capabilities: (1) Loopback-only binding via container port configuration (`-p 127.0.0.1:8283:8283` instead of `0.0.0.0:8283`), closing LAN accessibility entirely; (2) Letta's built-in `CheckPasswordMiddleware` activated with environment variables `SECURE=true` and `LETTA_SERVER_PASSWORD`, requiring `Authorization: Bearer <password>` header on every request.

For password storage, Daimon recommended and implemented DPAPI-based encryption via Python's `keyring` package instead of plaintext storage, closing a local trust-boundary gap: plaintext would be readable by any process running as Amos's Windows user, whereas DPAPI-encrypted credential storage via Windows Credential Manager ties decryption to the user and machine. The implementation cost minimal: six small dependency packages (pure Python wheels), two lines of code in `letta_ops.py` (`keyring.set_password()` / `keyring.get_password()`), and the existing shared request function in `letta_ops.py` updated once so all ~10 scripts inherit authentication automatically.

Amos queried risk vectors: the primary risk identified was operational (breaking tooling during rollout with a bad auth implementation), not catastrophic lockout — if authentication breaks, the container can be quickly recreated with `SECURE=false`; if the password is lost, the container itself still holds the value in plaintext env vars (retrievable via `docker inspect`); and worst case is a few minutes of downtime plus recreation since all actual memory lives in Neon (external Postgres), not the container.

Full implementation: container recreated with loopback binding and SECURE=true/LETTA_SERVER_PASSWORD, password generated via `secrets.token_urlsafe(32)` and stored in Windows Credential Manager, `letta_ops.py` auth header wiring verified end-to-end with both unauthenticated rejection (401) and authenticated success (200), `docker ps` binding confirmed loopback-only, and monitor.py's full check suite (including sleeptime invariant check) passed through the authenticated path. The password was displayed and Amos saved it into his password manager under the title "MemShepherd Letta Server" with lookup key `letta_server_password`. The old container (`memshepherd-letta-old`) was pinned as a rollback backup. The security work closes the last genuinely open exposure class from the convergence investigation.
