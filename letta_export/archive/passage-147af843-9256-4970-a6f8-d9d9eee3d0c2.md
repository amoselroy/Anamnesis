SUMMARY
During migration, 13 of 35 entries failed Neon insertion with HTTP 500 errors. Initial investigation appeared to support the recurring "section 4/4" failure issue pinned as a Letta/Neon database interaction problem. However, detailed analysis of Letta container logs revealed the actual root cause: Voyage AI rate limiting. The free tier had been reduced to 3 requests per minute (RPM) without a payment method. When Letta attempted to embed vectors during bulk inserts, it hit Voyage's 429 rate limit, which Letta surfaced back to Claude Code as HTTP 500.

This discovery also explained the recurring "section 4/4" failures in normal session archival: any session with 4+ archival sections would exceed the 3 RPM limit on later sections, causing silent failures that appeared to be database issues but were actually rate limiting.

Daimon implemented a multi-part fix: added `insert_archival()` retry logic (3 attempts with 25-second backoff), added 2-second inter-insert delays to all bulk archival loops as defensive spacing, and preserved the 13 failed entries to `queue/world_meta_retry.json` for recovery. Amos added a payment method to Voyage AI (enabling 300 RPM standard rate limits while maintaining the 200M free monthly tokens), and the 13 entries were successfully re-inserted without error.
