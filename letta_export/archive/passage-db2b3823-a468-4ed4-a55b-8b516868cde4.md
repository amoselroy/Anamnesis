WORLD PATTERN 2026-07-02 — Fail-fast lock acquisition is simpler and faster than bounded waiting — 2026-07-04

PRINCIPLE: When a worker cannot acquire a resource, polling with a deadline adds latency for no freshness benefit; immediate failure lets the caller apply its own retry logic intelligently.

NARRATIVE: During lock-mechanism design, an initial approach had `SessionStart` poll for the worker lock with a bounded deadline (wait up to 150 seconds for SessionEnd's background worker to finish). This seemed reasonable — let the sync operation complete rather than immediately failing. But analysis revealed: if something else already holds the lock, waiting doesn't make the result fresher; it just delays the inevitable retry. And if a stuck background worker is holding the lock, the deadline will eventually expire anyway, so the bound doesn't actually solve the problem. The simpler and faster approach was fail-fast: every caller tries once, and if the lock is held, immediately fails. SessionEnd fails fast (nothing waiting on it) and lets the queued files remain for next session. SessionStart fails fast and falls back to reading current block state (safe, possibly stale, better than blocking). Each caller now has clean semantics: either I hold the lock and proceed, or I don't and back off. No waiting, no polling complexity, no latency cost for a freshness benefit that doesn't actually arrive.
