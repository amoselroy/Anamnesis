SUMMARY
Daimon proposed a solution: run the same heavy `process_queue()` work at `SessionEnd` asynchronously as a head-start, keeping the synchronous `SessionStart` call as a correctness backstop. User correctly asked whether this risked reintroducing the original lag if SessionEnd's async work didn't finish before a quick restart. Daimon clarified: the design is additive, not replacing. SessionEnd fires async to drain the queue during idle time; SessionStart's sync call still runs, and in the common case (multi-hour gaps) it finds the queue already drained and exits quickly. In the quick-restart case, it picks up whatever the async worker left unfinished and completes synchronously — no regression from current behavior, only improvement for the common case.

User advocated for a component-based approach to avoid divergence: rather than splitting the script or adding caller-sensitive branching (`if from_session_end: ...`), extract parameters (`--budget-seconds`) to make the behavioral difference explicit and data-driven. Daimon implemented this: `process_queue()` now accepts `budget_seconds=None` (unlimited if omitted, stops between files if set), `--no-context` flag for SessionEnd calls (no additionalContext to inject), per-file claiming via atomic O_CREAT|O_EXCL sidecar files, and updated `settings.json` to call the identical script with different parameters from two hooks.
