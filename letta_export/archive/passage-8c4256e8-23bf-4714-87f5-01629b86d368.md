NARRATIVE SUMMARY:

A critical safety concern emerges: the pipeline writes to the Neon database (pgvector table) before writing the physical archival passage to storage. If anything fails between these two writes, the database ends up with an entry pointing to a passage that doesn't exist — an orphaned record.

**The Scenario**: Worker calls `insert_archival()` which performs two operations: (1) inserts row into Neon with passage content and vector, getting back a `passage_id`, (2) writes the passage to storage. If step 2 fails, step 1 has already committed an orphaned entry.

**The Fix**: Implement a two-phase commit pattern. After Letta returns the segmented narratives, immediately write them into the `.pending.json` file with `passage_id: null`. Then, for each section, attempt insertion to Neon and update the file with the returned `passage_id` after success. If insertion fails for a section, that section stays with `passage_id: null` and is retried on the next worker run.

**Idempotency Protection**: On retry, the worker reads the pending file and skips sections that already have a `passage_id` (already inserted to database). Only null-`passage_id` sections are retried. This prevents duplicate database entries and duplicate Letta calls.

**Resilience Guarantee**: No orphaned database entries can exist. Every database entry has a corresponding physical passage that was written after the database insert succeeded. The pending file serves as the source of truth for what's been queued and what's been inserted.
