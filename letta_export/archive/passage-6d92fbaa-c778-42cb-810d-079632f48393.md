SUMMARY
Amos observed that two ALCAR papers were scored tier 2 (indirect) when their classification was uncertain from title alone. This prompted discussion of fetching abstracts to improve Haiku's scoring accuracy. The constraint was strict: fetching abstracts during every research run could increase API call volume and token costs unacceptably. The solution: add abstract fetching *only to the Rank Papers endpoint* — a deliberate, manual per-therapy action where cost is acceptable. A new `_fetch_pubmed_abstracts()` function was implemented to batch-fetch abstracts for multiple PubMed IDs in one HTTP call, then `_score_source_relevance()` was updated to accept an optional `abstracts` dict and include the first 500 chars of each abstract in the scoring prompt. Non-PubMed sources (ICTRP, AlzForum) continue scoring on title only. Research runs remain unchanged — fast and cheap. Rank Papers now fetches abstracts live on-demand, passes them to Haiku, then discards them (no storage overhead). A failsafe was built in: if the abstract fetch fails, the function returns an empty dict and `_score_source_relevance()` falls back to title-only scoring for any papers without abstracts. After implementation, testing revealed a bug in the scoring function: the unpacking of the `sci` tuple (previously 2-tuple `(source_id, title)`, now 3-tuple `(source_id, title, url)` after adding URLs for efetch) was broken, causing a silent `ValueError` that swallowed the entire scoring result. The fix was defensive unpacking: `(source_id, *_)` handles any tuple size. After fixing, Rank Papers resumed working. The abstract fetching added a few seconds to manual ranking but provided better context for classification. Amos noted difficulty confirming whether Haiku was actually using the abstracts, highlighting the value of logging or explicit return metadata in future LLM integrations.
