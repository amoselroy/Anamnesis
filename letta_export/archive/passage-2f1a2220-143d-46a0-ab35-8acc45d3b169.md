SUMMARY
While documenting the changes, Daimon discovered a second, separate race condition: `world_trim.py`'s sync-mode operation (`run_sync()`, no arguments) also performs GET-then-PATCH on the exact same `world/patterns` block as `chunk_archive.py` (same `BLOCK_ID`), with zero awareness of the worker lock mechanism. Within a single SessionStart, this isn't a problem — hooks run sequentially and Hook 1 (world_trim.py) finishes before Hook 3 (chunk_archive.py) starts. The danger is cross-session: a still-running SessionEnd background worker from the previous session's close can race against SessionStart's `world_trim.py` sync trim, both trying to write the same shared block with the last write winning.

To avoid duplicating locking logic (which would risk divergence), Daimon extracted the worker lock into a new shared module `worker_lock.py` imported by both `chunk_archive.py` and `world_trim.py`. The extracted module contains the staleness-reclaim logic, lock acquisition/release, and path constants. Both scripts now import and use the identical lock. `world_trim.py`'s sync mode wraps its block-update operation with the worker lock, ensuring only one script (or one invocation of a script) writes to shared blocks at a time. Verified with sequential and contention testing.
