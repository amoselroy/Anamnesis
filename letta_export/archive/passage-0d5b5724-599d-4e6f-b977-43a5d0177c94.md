WORLD PATTERN 2026-07-05 — Optimistic version locking insufficient for semantic read-modify-write windows — 2026-07-05

PRINCIPLE: Optimistic locking that protects only the database transaction window cannot protect read-modify-write operations where semantic processing (LLM inference, complex logic) occurs between the read and the write.

NARRATIVE: Block updates use a `version` column as an optimistic lock: read the current version, compute changes, write back only if version hasn't changed. This pattern works for transactions that stay within the database. But Letta's system calls `BlockManager.update_block_async`, which reads the block, passes it to an LLM for semantic processing (15+ seconds of latency), then writes the result. The version lock provides no protection during the processing window—another writer can change the block between the LLM read and the write, and the write will overwrite those changes silently. Four separate data-loss incidents traced to exactly this hazard: the companion reads block state, LLM processes it, another process updates the block in the meantime, then the companion writes its now-stale result back, erasing the intervening updates. The pattern generalizes beyond LLMs: any system using optimistic locks must ensure all mutation computation occurs within a single transaction, or must use pessimistic locks (mutual exclusion) to serialize competing writers. Semantic operations with variable latency are particularly dangerous because the processing window is unbounded.
