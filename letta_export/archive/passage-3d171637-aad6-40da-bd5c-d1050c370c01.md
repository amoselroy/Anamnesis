WORLD PATTERN 2026-06-19 — Gunicorn worker timeout as root cause of hanging HTTP endpoints — 2026-06-19

PRINCIPLE: When an HTTP endpoint handler takes longer than the gunicorn worker timeout (default 30 seconds), gunicorn kills the worker process, terminating in-progress operations; the client sees an indefinite hang, not a timeout error.

NARRATIVE: Amos reported that clicking "Summarize" displayed "Generating..." for 5+ minutes with no response. Initial hypothesis was LLM API timeout, but investigation revealed Render's gunicorn server kills any worker that doesn't respond within 30 seconds. The endpoint was making 3 sequential LLM calls totaling 45+ seconds, so gunicorn killed the worker mid-operation. The client saw no error (gunicorn doesn't signal connection death back to the browser), just hung indefinitely. The fix wasn't faster operations but architectural: move work to a background daemon thread that returns immediately (under 1 second), so gunicorn sees a successful response and the thread continues independently. This pattern applies universally to any long-running operation on gunicorn-backed services: if work takes longer than ~20 seconds (safety margin before timeout), background threads are required. The insight is that the hang appears to be an API timeout but is actually a server process timeout — two very different failure modes requiring different fixes.
