WORLD PATTERN 2026-06-29 — Relationship-level data storage creating mandatory UI context requirements — 2026-07-01

PRINCIPLE: When data is stored at a relationship level (therapy_conditions rather than therapies), the UI becomes architecturally required to surface context continuously rather than optionally, because scores become meaningless without indicating which condition's context they represent.

NARRATIVE: During homepage redesign, Daimon discovered that effectiveness and evidence scores weren't displaying in the main listing view — they returned NULLs because the query read from the therapies table directly, but scores were stored in therapy_conditions. This revealed a deeper architectural constraint: since scores are condition-specific, showing them without condition context creates either meaningless empty columns or misleading scores from an arbitrary condition. The solution wasn't to pick one condition globally but to make Alzheimer's Disease the default explicitly and prominently visible via a banner. This pattern generalizes: whenever data is denormalized into relationship tables, the UI must maintain awareness of and communicate the relationship context continuously. The context isn't optional scaffolding — it becomes part of the data's meaning. This applies to any multi-tenanted, multi-condition, or multi-entity system where scores, statuses, or metadata are keyed by relationship rather than by the primary entity alone.
