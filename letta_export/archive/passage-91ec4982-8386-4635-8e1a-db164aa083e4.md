SUMMARY
When adding a new therapy "Cu(ATSM)" (copper-ATSM for Alzheimer's treatment) via the admin console, the user discovered that the therapy was created successfully and generated summaries and papers correctly, but was not automatically linked to Alzheimer's disease and news search returned no results. Investigation revealed two separate problems: (1) the `create_therapy` endpoint does not automatically insert into `therapy_conditions` after therapy creation, making the therapy invisible in condition-filtered views despite being functional, requiring manual condition linking via a separate API call; (2) the therapy's slug used parentheses (`Cu(ATSM)`) which broke the Google News query string nesting — the query builder concatenates search terms inside existing parentheses, causing `(Cu(ATSM)) Alzheimer (site:...)` to be malformed. The first problem was identified as a workflow friction point that "may happen often" when new therapies are added. The second was fixed by updating both the Google News query builder in `scrape_news_for_therapy()` and the standalone `scrape_google_news()` function to quote each individual search term before concatenation, preventing parentheses in therapy names from breaking the query structure. To address the workflow problem systematically, the admin console was enhanced with a condition picker UI: checkboxes for available conditions are displayed during therapy creation, and the submit handler now automatically links selected conditions via the `POST /conditions/{slug}/therapies/{therapy_id}` endpoint after creation. This prevents the discovery and friction that occurred with Cu(ATSM), where the therapy was functional but invisible to users navigating from the main Alzheimer's condition page. The incident revealed a broader principle: new entity creation that requires cross-table linking should make that linking frictionless and visible at creation time, not as a separate manual step.
