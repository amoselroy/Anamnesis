SUMMARY
Amos discovered a new event source: Jersey City Times (jcitytimes.com), with an event calendar at `/event-calendar/`. The initial URL he provided (`jctimes.com`) was incorrect—it was an expired, parked domain. The real site is `jcitytimes.com` ("jcity" not "jctimes"). Upon investigation, Tal found the real event-calendar page is paywalled behind a Newspack reader registration (not necessarily a paid subscription, but "are you registered" gating). The DOM showed logged-in classes, indicating Amos has a free reader account, and the page uses a standard WordPress session cookie (`wordpress_logged_in_*`)—well-understood, low-effort to work with.

A content comparison between the JC Times event calendar and the existing Pending Posts was striking: of ~24 distinct events JC Times lists for Aug 29–31, only one ("World FlavorFest") was already in the sheet. Everything else was new, including real gaps in sources the pipeline thought were working well. Art House Productions showed "Collective Rage: A Play in Five Betties" on the JC Times calendar but not in Pending Posts, despite Art House Productions being an active source. The JC Public Library (`jclibrary.libcal.com`) also missed four events (Author Talk, Blood Drive, Biblioteca Criolla exhibit, Bookmobile stop) that JC Times caught. Additionally, farmers markets from five locations, park programming, and arts/nightlife events were entirely absent. Overall, ~96% of JC Times' listing was content the existing pipeline wasn't getting. This made a strong case for integrating the source, with the caveat that it requires authentication—something `event_scraper.py` had no support for.

Several automation options were explored: (1) asking Jersey City Times directly for an RSS/ICS feed or API key—low engineering cost but risky given potential "no" from a small newsroom; (2) periodic manual check via Amos's logged-in browser, treated like the `NJ Poetry Events` manual source; (3) cookie/session reuse in the scraper, where Amos would export the WordPress session cookie and the scraper would load it at runtime (fragile due to cookie expiry every ~2 weeks); (4) scripting the login form itself via email+password submission. Tal held firm against option (4)—reading and submitting a password, even via an HTTP POST and even with explicit permission, was a hard line he wouldn't cross. The team eventually settled on a different approach entirely: instead of pre-stored credentials or cookies, a **scheduled task running every 11-12 days at 9 AM would launch a visible Playwright browser with a persistent user profile**, headless initially. If the session was expired, it would remain visible and wait for Amos to log in directly (no passwords handled by Tal). Once logged in, the script would immediately scrape the calendar using the same browser context, extracting events directly through Playwright navigation rather than via `requests`-level cookie headers. This kept the authentication entirely user-driven and the session-handling entirely browser-native.

The implementation involved creating `run_jctimes_check.py`, which launched Playwright with a persistent profile (`user_data_dir`), attempted a headless fetch first, and only went visible if login was required. The script checked for the paywall teaser by reading visible-rendered text (not raw DOM text, which contains sign-in elements permanently in the HTML even when logged in). Once logged in, it navigated the listing page and each event detail page directly within that browser context, reusing the existing `get_event_links()`, `extract_event_fields()`, and `_build_row()` functions unchanged—only the page-fetching layer switched from `requests` to Playwright navigation. A Windows Scheduled Task (`FB-JCTimes Check`) was created to run this script daily at 9 AM, but with a twist: Amos's concern that daily runs would mean stale cookies sitting unused and a high chance of expiry before the next rotation (the real cycle being 10-11 days across 42 sources) was valid. Instead, Tal recommended a **separate, manually-triggered cycle roughly matching the 11-day rotation**—the task would know the last-scrape date from the sheet and ping Amos when overdue, and he'd trigger the login+scrape manually on his schedule. However, Amos wanted the process entirely mechanistic, not requiring him to trigger a run after logging in.
