SUMMARY
During the Hudson Realty implementation, the discussion surfaced a broader question about state management: should the growing deduplication lists be trimmed periodically, or allowed to grow indefinitely? The analysis was straightforward — for deduplication purposes, only a rolling window of recent entries is needed; old entries from months ago will never reappear in the feeds, making them dead weight in memory.

The solution implemented a simple trim pattern: every save operation on the state file trims the `shared` list to the 500 most recent entries using Python's slice notation `[-500:]`. Since the list is append-only (oldest entries at front, newest at back), this maintains FIFO behavior while capping the file size. The observation was raised: should the same trimming pattern be applied to `re_poster.py` and `promo_poster.py`? This was identified as a follow-up task requiring review of how each poster manages state before implementation.
