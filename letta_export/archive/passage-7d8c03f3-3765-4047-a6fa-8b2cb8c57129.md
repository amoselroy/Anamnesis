SUMMARY
After a forced session compaction, resumed investigation of the critical unsolved bug: the index page condition filter was returning "no therapies" even when Alzheimer's Disease was specifically selected, despite the database containing 5 linked therapies. Initial hypothesis focused on transaction state corruption in the database layer (psycopg2 connection left in aborted state by `_resolve_condition_slug`'s exception handling). Upon re-entering the session, examined the frontend JavaScript in `index.html` and discovered the actual root cause: the `onFilterChange()` function was calling `doSearch()` instead of `loadList()` when the user had previously performed a search (identified by checking `currentMode === 'search'`). The search code path requires `t.embedding IS NOT NULL`, which filters out any therapies without embeddings. Since no therapies had been through Research & Summarize re-runs yet, all embeddings were NULL, resulting in zero results. The fix is a single-line change: removing the `|| currentMode === 'search'` condition from `onFilterChange()` so an empty search box always triggers `loadList()` instead of persisting search mode. This distinguishes between "user typed search terms" (which should filter) and "we previously did a search but now the user is using the condition filter" (which should reset to list mode). The bug was subtle because it only manifested when users: (1) performed a search first, then (2) tried to use the condition filter, creating an expectation mismatch between frontend state and query requirements.
